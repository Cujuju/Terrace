# Performance review — 2026-08-29

Scope: whole-repo perf audit against the project bar (>=140 fps on the owner's
machine, ~7.1 ms client frame budget; server tick period 100 ms at
`DEFAULT_TICK_HZ = 10`, `server/src/config.ts:110`; default world is 2048 cells,
`shared/src/constants.ts:59,67`).

Every finding below was re-verified from primary source at the cited `file:line`
by a second reviewer, and every cost was either re-measured independently or
re-traced with real sizes. Where the original claim's magnitude did not survive,
the **Skeptic's corrected cost** line is the number that stands — quote that one,
not the finding's headline. 25 findings held; 11 were refuted (appendix).

Nothing here was filed as an issue and no code was changed.

## Section A — Client frame, paid on EVERY frame

These are the only findings that come out of the 7.1 ms budget unconditionally.
Ranked by measured per-frame cost.

### A1. The layer-edge overlay draws one `LineSegments` per chunk — ~13 000–16 384 scene objects on a revealed default world
- **File:** `client/src/render/layerEdgeOverlay.ts:280` (`rebuild` → `new BufferGeometry` + `new LineSegments` + `group.add` at :248–285)
- **Mechanism:** driven per chunk by build completion (`client/src/world.ts:532` `onChunkDrawn` → `refreshChunk`), created unconditionally for every world (`client/src/world.ts:507`) — unlike the query-gated pick-debug overlay at `client/src/main.tsx:195-197`. `CHUNK_SIZE = 16` cells (`shared/src/constants.ts:33,101,110`), so a 2048-cell world is 128×128 = 16 384 chunks; `neighboursKnown` (`layerEdgeOverlay.ts:236-246`) only drops the frontier ring. Every object is walked by three's `updateMatrixWorld` + per-object frustum test each frame, before culling.
- **Cost:** ~3.1 ms of main-thread CPU per frame at the default world size, ~43 % of the budget, before the ~1 400 survivors are submitted.
- **Fix:** give the overlay the super-mesh arena terrain and fog already have (`client/src/render/terrainMeshes.ts:435` `SUPER_MESH_SPAN_CHUNKS = 8`; `client/src/render/frontierFog.ts:687-712`) — 16 384 → 256 objects. Do **not** gate the resting cyan meshes behind a debug flag: `layerEdgeOverlay.ts:1-3` records the owner asking for exactly that drawn-on-the-map affordance (2026-08-23).
- **Skeptic's corrected cost:** measured, 200 timed frames of `updateMatrixWorld` + three's per-object frustum-sphere test over 16 384 `LineSegments` using the repo's own three build: **3.07 ms/frame, 0.187 µs/object** (0.069 ms at the 319 objects the plan measured at 512 cells). The finding's 14.7 ms is **refuted**: it divides a whole `renderer.render` pass by its draw-call count, a rate the baselines contradict (`.gpu-perf/results/…frostwick512.json` 274 calls / 1.277 ms = 4.7 µs; `…fresh2048-14weather.json` 160 calls / 1.170 ms = 7.3 µs — per-call cost *falls* as call count rises), and it counts every object as an uncullable draw call. Caveat: 0.187 µs/object is Node/V8 on Linux, ±~1.5× vs Chrome on the owner's box; the 1 390 post-cull survivors are one camera framing, not a bound.

### A2. Every creature carries its own `Skeleton`, and its own 10-node subtree
- **File:** `client/src/render/rigSkin.ts:350` (per-instance `Skeleton`; fresh `Bone`s at :334, `SkinnedMesh` per surface at :354)
- **Mechanism:** `plugins/wildlife/client/index.ts` `renderFrame` animates every view with no visibility or distance gate. three then charges per skeleton per frame (`three.module.js:4740-4752` `skeleton.update()`; `three.core.js` sets `boneTexture.needsUpdate`; `three.module.js:18639-18653` binds it per skinned draw). Wildlife cap is 850 + 18 birds.
- **Cost:** ~2.3–2.5 ms/frame at cap — ~32 % of the budget.
- **Fix:** per-species `InstancedMesh` with the pose in an instance attribute (or a shared batched bone texture indexed per instance) — the same "unit of authoring is not the unit of drawing" collapse `rigSkin.ts`'s own header describes, one level up. The cheap partial (gate `animate`/skinning by visibility) recovers only the frustum-gated part.
- **Skeptic's corrected cost:** measured headless (real `createWildlifeModels()`, three 0.185.1, N=850, no GL): **2.30–2.50 ms/frame total**, decomposed as `scene.updateMatrixWorld` over 8 332 Object3Ds **1.16–1.20 ms (NOT gated by culling)**, `skeleton.update` ×850 **0.47 ms (frustum-gated — 0.11 ms at 25 % visible)**, plugin `animate` 0.13 ms. So the Skeleton-specific share is 6.6 % of budget, not 31 %; the dominant cost is the per-entity Object3D subtree walk, which only removing nodes fixes. Bone counts measured from the real rigs: fish 4, grazer/bird 8, whale 10, deepsea 7 — so "868 texture uploads / 1 736 skinned draws per frame" is a never-observed ceiling (real captures show 316 total draw calls for the whole scene). Boats (real fleet is single digits, not the 2048 payload cap) and pilgrims (46) contribute nothing measurable — **scope this to wildlife**. Unverified assumption: that the wildlife broadcast is world-wide rather than per-client reveal-filtered.

### A3. `pickWorldCell` raycasts the whole declared forest, once per frame while a tool is held
- **Files:** `client/src/plugins/host.ts:386` (`intersectObjects(pickableObjects, true)`, no `far` set at :379) and its only per-frame caller `plugins/fire/client/index.ts:543` (inside `ctx.onFrame`, gated on `torchHeld && pointerMoved`)
- **Mechanism:** flora declares two world-spanning roots (`plugins/flora/client/index.ts:348,354`); trees are `InstancedMesh`es whose `raycast` walks every live instance with no acceleration structure. `models.ts:222-228` recomputes the bounding sphere on every `apply()`, so the whole-mesh early-out effectively never fires for an on-canvas ray. Fire is the **only** per-frame caller in the repo; everything else picks from a press handler.
- **Cost:** ~0.7–1.0 ms/frame while the torch is held and the pointer moves over a mature world; ~10–14 % of the budget. Scales linearly with tree count, so it is negligible early in a world.
- **Fix:** extend `markPickable` so a registrant supplies a cell-space occupancy lookup (flora already keys trees by cell) and resolve object picks by the same height-field ray march `pickTerrainCell` uses (`host.ts:319-331`). Narrow guard meanwhile: set `pickRaycaster.far`, reject subtrees whose world bbox the ray misses, and gate fire's re-pick on the cursor having moved a screen-space threshold (it only needs a *cell*).
- **Skeptic's corrected cost:** two independent re-measurements, both below the claims. (a) 200 warm picks, 4 096 trees scattered over a 2048 world: **0.72–0.85 ms median, 1.5 ms warm max** — and **paid in full on a miss** (aiming at empty sky measured 0.732 ms with 0 hits, because the recomputed sphere spans the world), which makes the finding *stronger*, not weaker. The claimed 12.39 ms max is cold-JIT/GC noise. (b) A second bench counting only live instances — `models.ts:213-220` writes each tree into `trunks` plus exactly one crown mesh, and `raycast` iterates `count`, not capacity, so a saturated forest is 8 192 raycast instances, not 12 288 — gave **0.80 ms at 4 096 trees, 0.37 ms at 2 048, 0.10 ms at 512**. The 2.28 ms asserted in the comments at `host.ts:375` and `fire/client/index.ts:467` is unsourced and above anything reproducible. Impact: medium.

### A4. Skiff fleet recomputes and re-uploads its full instance buffer every frame
- **File:** `plugins/structures/client/skiffModels.ts:136` (`writeFrame`; `needsUpdate` at :168, `computeBoundingSphere()` per mesh at :169; `animate` calls it whenever any skiff exists, :184-187)
- **Mechanism:** per part-mesh (2) × per skiff: 2 sin + cos + `atan2`, `Quaternion.setFromAxisAngle`, `Matrix4.compose`, `multiplyMatrices`, `setMatrixAt`. No `addUpdateRange`, so `WebGLAttributes.updateBuffer` takes the `updateRanges.length === 0` branch and `bufferSubData`s the whole capacity array (`SKIFF_INSTANCE_CAPACITY = STRUCTURES_CAP(512) × SKIFF_MAX_PER_SETTLEMENT(3) = 1536`). The union bounding sphere spans the world, so the meshes are effectively never culled, and `rebuild` feeds every structure in the world — there is no view or distance culling upstream.
- **Cost:** ~0.4 µs per live skiff per frame, plus a fixed 196 608 B/frame upload.
- **Fix:** `addUpdateRange(0, count*16)` before `needsUpdate`; replace the quaternion/compose with a direct 4×4 write (Y-rotation + translation, constant local matrices); derive the sphere analytically from anchor cells + orbit radius, or refresh it only on `apply()`.
- **Skeptic's corrected cost:** reproduced independently (2 000 iterations after warmup, real modules + three 0.185.1): 0.018 ms @48 skiffs, 0.072 @192, 0.146 @384, 0.299 @768, **0.623 ms @1536 (cap)**. A typical coastal world (64–128 coastal settlements ≈ 192–384 skiffs) is **0.07–0.15 ms, 1–2 % of budget**; cap worst case 8–9 %. Only the **196 608 B/frame** `bufferSubData` (~27 MB/s at 140 fps, even with 10 skiffs afloat) is genuinely count-independent — that half is traced, not GPU-measured. Impact: medium at cap, low-to-medium typically.

### A5. Mover render loops allocate a Map, an entity object, a closure and six arrays per entity per frame
- **File:** `plugins/wildlife/client/index.ts:149` (per-creature closure inside the loop); `plugins/wildlife/client/interpolation.ts:145-166` (`sample()` allocates a fresh Map + one object per entity); `plugins/wildlife/client/placement.ts:402-408` and `:513-519` (`walkerGroundY`/`swimmerSeabedY` rebuild an array-of-five-arrays per call; `as const` is type-only and does not hoist)
- **Mechanism:** `renderFrame` is registered unconditionally (`index.ts:240`) with no population or visibility early-out; drawn population cap is 850 + 18. Same shape duplicated in `plugins/boats/client/interpolation.ts:132-152` and `plugins/pilgrims/client/interpolation.ts:93`.
- **Fix:** hoist both offset tables to module-level flat consts and hoist the `sample` closure out of the loop (it captures only `ctx`); have the interpolators refill one persistent Map of mutable pose records instead of rebuilding both.
- **Skeptic's corrected cost:** **~0.159 ms/frame avoidable at the 850-entity cap (~2.2 % of budget)** — measured 0.184 ms/frame current shape vs 0.025 ms/frame hoisted/pooled, real modules under Node with an O(1) height stand-in. 0.016 ms/frame at 100 creatures. Not the claimed 0.289 ms / 4 %. Also corrected: `sample()` is called **once** per message in `receive` (`interpolation.ts:93`), not twice. Held anyway — unconditional, per-frame, hard-capped, duplicated in three plugins, and the fix is a pure hoist. Impact: low.

### A6. daynight builds a fresh `Intl.DateTimeFormat` every rendered frame
- **File:** `plugins/daynight/client/formatTime.ts:46` (`new Date(...)` + `new Intl.DateTimeFormat(...)` per call, :45-50)
- **Mechanism:** `plugins/daynight/client/index.ts:141` registers `onFrame` unconditionally in `attach()`, and the `setWorldTimeText(formatWorldClock(...))` call at :150-152 sits **above** the reduced-motion early-return at :155, so even the reduced-motion path pays it. `client/src/render/scene.ts:346,357` runs frame callbacks synchronously inside rAF. The plugin is in the default list (`client/src/plugins/registry.ts:11,40`). The output is minute-granular; the formatter is rebuilt ~140×/s.
- **Fix:** hoist the formatter to a module-level const (locale `undefined`, `timeZone` fixed `'UTC'` — no per-call state), optionally short-circuit when `totalMinutes` has not moved. No locale listener needed; page locale cannot change without a reload.
- **Skeptic's corrected cost:** independently reproduced, 3 × 20 000 iterations, node v24.19.0: **36–68 µs per call** (58.6 / 68.3 / 35.9) vs **0.84–0.91 µs hoisted** — a 40–70× gap, ~0.5–1.0 % of the 7.1 ms budget, ~5 ms of main-thread time per wall-clock second at 140 fps. State it as a range, not the flat 51 µs. Caveat: measured in node V8, not Chrome on the owner's Windows box (same engine and ICU path, not directly verified). Behaviour-identical one-line fix.

### A7. Cyclone deck re-uploads 133 KB of unchanged instance data every frame, at full pool capacity
- **File:** `plugins/storms/client/spiral.ts:381` (`update`; rewrite loop :390-441, six range-less `needsUpdate` flags :443-448)
- **Mechanism:** `plugins/storms/client/index.ts:281-282` calls `spiral.update` every frame. Buffers are capacity-sized (`MAX_SPIRALS(2) × PUFFS_PER_SPIRAL(810) = 1620`, `spiral.ts:57,67`, attributes :328-332), so a single 810-instance cyclone uploads all 1 620 slots. Everything written changes only on a server push (5 Hz); the animation is already a `uElapsed` uniform. The file's own header (`spiral.ts:9-11`) claims "nothing per frame in between" — the code does the opposite. Same defect smaller at `plugins/volcanoes/client/plume.ts:415-419` and `plugins/storms/client/funnel.ts:584-592`.
- **Fix:** the repo already has the pattern next door — `plugins/volcanoes/client/lavaFlow.ts:557-563` does `clearUpdateRanges()` + `addUpdateRange(...)`. Better: restore the header's design — write instance data in `apply()` (the server push) and leave `update()` to set `uElapsed`/`uDaylight`/`mesh.count`. Only `strength` needs a per-frame path, and that is one float, not six buffers.
- **Skeptic's corrected cost:** **~0.02–0.05 ms/frame while a cyclone is live, zero otherwise** (early-out at `spiral.ts:399-402`, which the finding missed): 0.010–0.020 ms CPU for the rewrite loop + one 136 080 B `bufferSubData` across six range-less buffers ≈ 18.6 MB/s at 140 fps — negligible bandwidth on any modern bus. **Under 1 % of the budget; impact low, not medium.** Real per-frame defect and a contract violation replicated across three renderers, but not a frame-budget threat.

## Section B — Client frame, paid per sculpt step / per delta

Bursty, but every one of these lands synchronously on the main thread inside a
websocket handler, i.e. inside whatever frame the message arrives in. A held
sculpt repeats at `SCULPT_REPEAT_INTERVAL_MS = 120` (`client/src/config.ts:270`),
so the realistic rate is ~8/s, rising toward once per frame on a fast drag.

### B1. Every grass delta rebuilds the whole meadow synchronously
- **File:** `plugins/flora/client/index.ts:177` (`rebuildGrass`, called unconditionally from both handlers at :417 and :423)
- **Mechanism:** `grassPlacementsFor` walks every cell with one `ctx.terrainHeightAt` each (`client/grassPlacement.ts:28-53`); `grassModels.apply` composes `GRASS_BLADES_PER_TUFT = 5` matrices per tuft with 2 `setMatrixAt` per blade (`client/grassModels.ts:493-570`). A one-cell uproot costs the same as a full resend. Server broadcasts on every sculpt diff that touches a tuft (`plugins/flora/server/index.ts:913-955`). No coalescing exists on main.
- **Fix:** make the rebuild proportional to the delta — the populations are cell-keyed Maps already, so a cell→slot free list with swap-remove compaction touches only `apply` and the two handlers. Failing that, mark dirty in the handler and do at most one rebuild per `onFrame`.
- **Skeptic's corrected cost:** measured independently (three 0.185.1, faithful `apply` incl. `computeBoundingSphere`, median of 15 after warmup): **3.93 ms @4 293 tufts, 5.69 ms @6 101, 10.28 ms @10 846, 64.05 ms at `FLORA_GRASS_CAP` = 40 960**. The finding's population is **refuted**: 10 846 is a count of green *cells* (`protocol.ts:849-854,1359`), which `FLORA_GRASS_SHARE_OF_256` thins to ~6 100 tufts. So the shipped-512 figure is **~4–6 ms, 55–80 % of the budget**, not "2.0× the budget"; drop the "~120 ms of main-thread JS per second" framing. The 64 ms cap figure is genuinely reachable on the default 2048 world, since `FLORA_GRASS_CAP` is world-size-independent. Both figures use a constant-time ground stub, so real cost is strictly higher.

### B2. `computeBoundingSphere` re-derives every instance transform `apply` just wrote
- **File:** `plugins/flora/client/grassModels.ts:568` (`:562-569`, all three grass meshes). Same call at `fringeModels.ts:398`, `models.ts:228`, `cropModels.ts:216`, `stumpModels.ts:295`.
- **Mechanism:** three's `InstancedMesh.computeBoundingSphere` loops `i < count` doing `getMatrixAt` (16-float copy) + `Sphere.applyMatrix4` + `union`, with no early-out — recomputing an extent the placement loop already knew from `placement.x/groundY/z` plus the per-tuft reach `assertBladeFitsTuft` (`grassModels.ts:403-427`) already proves. `frustumCulled` is not disabled, so the sphere is genuinely consumed — it must be computed cheaply, not dropped.
- **Fix:** accumulate min/max of `placement.x/groundY/z` in the existing loop and write `mesh.boundingSphere` directly, expanded by the proven reach. Repo precedent for exactly this substitution: `client/src/render/water.ts:591-599`, `terrainMeshes.ts:895-925`, `riverRig.ts:771-809`, `frontierFog.ts:562-606`. Implementer note: the expansion must include vertical extent (blade height × `GRASS_SCALE_MAX`, blossom at the tip), not just the horizontal reach the assert bounds.
- **Skeptic's corrected cost:** re-measured at the same instance counts (54 230 / 54 230 / 1 805): **median 6.91 ms** (min 6.72, max 7.80, 20 reps) — confirms the claimed 6.71 ms; **25.45 ms at `FLORA_GRASS_CAP`**. **Overlap warning:** this is a *component* of B1's rebuild at the same population, not an additional cost — do not sum them. Per grass rebuild (up to ~10 Hz while sculpting), not per frame.

### B3. Every `structures:changes` delta re-surveys a 748-cell disc for every structure the client holds
- **File:** `plugins/structures/client/placement.ts:69` (`surveySite` per structure); driven from `plugins/structures/client/index.ts:61-66` (`rebuild` over the whole `buildings` map) at :126-134 and :136-140, delta size never consulted
- **Mechanism:** `site.ts:76` `COASTAL_SEARCH_RADIUS_CELLS = cellsAcross(4) = 16` → `buildTightDisc(16)` = **748 offsets** (counted at runtime; the "37 cells" comment at `site.ts:68` is stale). For a coastal cell it allocates one `{x,y,distanceSquared}` per water cell, full-sorts (`site.ts:144-160`), `.map()`s a second array — to consume at most `SKIFF_MAX_PER_SETTLEMENT = 3` (`skiffs.ts:115`). No early-out is reachable: `client/src/world.ts:771` → `terrain/mirror.ts:65-70` clamps and never returns null, so `unknown` is always 0 and all 748 samples always run.
- **Fix:** cache each cell's `SiteSurvey` keyed by structure cell and re-survey only cells whose neighbourhood terrain changed (the client already has the terrain diff), so a delta costs O(changed). Inside `surveySite`, replace sort+map with a bounded 3-best selection over primitive dx/dy and early-out once both the coastal threshold and the 3 nearest are settled.
- **Skeptic's corrected cost:** independently measured (real modules, 2048² Int16Array + real `quantizeToBand`, 20 iters after warmup): **2.85 ms/rebuild for 512 all-inland** (~5.6 µs/structure), **9.74 ms with 70 % coastal** (~19 µs/structure coastal), 2.09 ms at 128 structures. The submitted 17.58 ms coastal figure **did not reproduce**. Cadence is narrower than "every delta": `server/index.ts:261` early-outs an all-empty broadcast and `reactToTerrain` (:568-595) only broadcasts when a house actually stood on an edited cell — so triggers are CA generations with a non-empty delta (15 s), the 60 s keepalive, join/unlock refresh, and **once per applied sculpt edit that demolishes** (the genuine per-sculpt tie: a drag over a village pays a full rebuild per edit). 512 is the world-wide `STRUCTURES_CAP` ceiling and sends are fog-filtered, so a typical client holds fewer. **~40 % of a frame inland, a dropped frame outright when coastal.** Impact medium-to-high.

### B4. Every sculpt step fully re-uploads three world-sized water textures (12.58 MB at 2048²)
- **File:** `client/src/render/water.ts:645` (`refresh` sets `needsUpdate` on all three textures at :645-647)
- **Mechanism:** `client/src/world.ts:427-435` `applyDirty` calls `water.refresh(mirror, dirty)` on every predicted sculpt and every non-empty authoritative diff, gating only on an empty set. The CPU-side texel write is correctly chunk-scoped (`client/src/terrain/waterDepth.ts:686-718`), but each texture is a `DataTexture(buffer, worldSize, worldSize, RedFormat, UnsignedByteType)` (`water.ts:222-225`, three allocated at :524-547 = 12.58 MB), and three 0.185.1's `updateTexture` with empty `updateRanges` issues `texSubImage2D(..., 0, 0, image.width, image.height, ...)` — the whole image (verified verbatim at `three.cjs:71778-71786`, including `const componentStride = 4; // only RGBA supported`). The comment at `water.ts:617-631` documents the cost and names the blocker, then accepts the full upload — the code confirms the comment.
- **Fix:** pack the three single-channel curves into **one** `RGBAFormat`/UnsignedByte world texture. That collapses 3 uploads into 1 and — the real win — makes `addUpdateRange` legal, because three's hard-coded `componentStride = 4` is exactly right for RGBA (`getRow` does `floor(index/4)`, which is the texel index). `refresh` then adds one range per dirty chunk row (16 rows × 2048 × 4 B = 131 KB for a two-chunk brush) instead of 12.58 MB — a ~96× reduction. `terrainMeshes.ts:932-955` already applies the identical range-not-flag pattern and documents why. **Carry the caveat:** one RGBA 2048² texture is 16.8 MB VRAM vs 12.58 MB today, and the full-upload paths (`world.ts:647,715`, `setWorldSize`) get 33 % more expensive — paid back many times on the sculpt path.
- **Skeptic's corrected cost:** sizes exact (2048² is the **default** world, not a stress case): **12.58 MB re-uploaded per sculpt step that dirties any chunk**. Priced with the project's own transfer estimator (`ARENA_TRANSFER_MS_PER_VERTEX`, `terrainMeshes.ts:180-200`, whose underlying measurement is 19–21 MB in 3.5–12 ms of `bufferSubData` plus roughly as much again in next-frame backpressure): **~2–7 ms of upload plus comparable backpressure per sculpt step**, against 7.1 ms. Treat the range, not the finding's 12.6 ms, as the claim — the rate is transplanted from `bufferSubData` to `texSubImage2D` (same ANGLE copy path, not separately measured). Rate corrected: **~8/s on a held stroke**, not per pointermove — `sculptInput.ts:246,656` gate emission on cursor *cell* change; three coalesces multiple `needsUpdate` before a bind, so "once per frame" is a fast-drag ceiling.

### B5. Fringe repeats the grass defect at a quarter scale
- **File:** `plugins/flora/client/index.ts:190` (`rebuildFringe`, with a fresh `Array.from(fringe, …)` per call) → `plugins/flora/client/fringeModels.ts:341-399` (`apply`, uncapped `needsUpdate` + `computeBoundingSphere` at :392-399)
- **Mechanism:** called unconditionally from both handlers (`index.ts:438`, `:445`) with no size gate; server side `plugins/flora/server/index.ts:941` `reactToEdit` per diff cell → `broadcastFringeChanges` :953. Buffers are capacity-sized: `FLORA_FRINGE_CAP(8192) × (3 reed + 7 heather stems) × base+tip × 64 B = 10.49 MB`, re-uploaded whole (`three.module.js:141-151`, empty `updateRanges` → whole-array `bufferSubData`, independent of `mesh.count`).
- **Fix:** same three fixes as grass, same commit — per-slot writes keyed by cell, `addUpdateRange(0, count*16)` before `needsUpdate`, bounding sphere from placement extents. Drop the `Array.from`; `fringePlacementsFor` can take the Map's entries iterator.
- **Skeptic's corrected cost:** measured (real modules, 30 iters, first 10 discarded): **2.6 ms at the shipped 512² population (2 789 plants, 95 % reeds), 4.0 ms at 4 000, 9.4 ms at the 8 192 cap reed-dominated, 16.9 ms at the cap all-heather.** Of the 4 000-plant cost: ~0.2 ms `Array.from`, ~0.2 ms placement alloc, ~2.7 ms compose/`setMatrixAt`, ~0.6–0.9 ms `computeBoundingSphere` — so the `Array.from` is ~5 %, less than the finding's framing implies. Corrections: heather carries **7** stems, not 6 (`protocol.ts:1551`; the `fringeModels.ts:31` "6 sprigs ≈ 9 MB" comment is stale) → buffer is **10.49 MB**; trigger is narrower than "every shoreline sculpt step" — `server/index.ts:532` early-outs when both lists are empty, so only a diff that actually contains a fringe-occupied cell fires it; and the combined "≈19 ms / ≈38 MB per shoreline step" is conditional on B1 holding.

### B6. Every lava delta rebuilds the whole flow mesh inside the message handler
- **File:** `plugins/volcanoes/client/lavaFlow.ts:358` (`rebuild`: fresh `covered` Map :369-388, fresh `capY` Map :391-404, full cap+riser emission :487-535), reached from the websocket handler at `plugins/volcanoes/client/index.ts:129-142`
- **Mechanism:** whole-mesh by design — a radius-4 disc (81 offsets, `FLOW_RADIUS_CELLS = cellsAcross(1) = 4`) stamped per flow cell over up to `LAVA_CELL_CAP = 192`. The 192 tracked cells are **world-lifetime**, not per-eruption, so any world with eruption history pays the full-cap rebuild from the first new cell of the next eruption.
- **Fix:** the rebuild-whole argument at `lavaFlow.ts:350-357` justifies rebuilding a *neighbourhood*, not the world — keep `covered`/`capY` as persistent state and re-stamp only cells within `FLOW_RADIUS_CELLS` of the tick's molten/forgotten cells (typically a handful). Note: the "coalesce per frame" half of the original fix is near-worthless — `apply` already costs at most one rebuild per message and messages are ≥100 ms apart. The value is entirely in the incremental re-stamp and Map reuse.
- **Skeptic's corrected cost:** measured on the **real module** (not a replica): **0.745 ms per rebuild at the 192-cell cap** (11 274 verts), 0.253 ms @64 cells, 0.160 ms @32 — 10.5 % of the budget. Frequency corrected **down**: `FLOW_SPEED_CELLS_PER_SECOND = cellsAcross(0.5) = 2` (`server/flow.ts:62-63`), so one erupting vent melts a cell every 5th tick → **2 rebuilds/s per vent**, not 10; 10/s needs ~5+ of the 8-vent cap erupting at once. Two early-outs under-credited but not saving: `apply` returns when neither list moved a cell (:614-617), and a molten cell at cap with no matching `forgotten` is skipped (:588) — neither applies in steady state, because `evictVolcanoes` evicts one per new one and ships it in `forgotten`.

## Section C — Client GPU (upload volume)

### C1. Flora instance-matrix uploads are sized by CAP, not population — 28 MB (grass) + 10 MB (fringe) per rebuild
- **File:** `plugins/flora/client/grassModels.ts:564` (`needsUpdate`, no update range, :562-569); same at `fringeModels.ts:392-396`, `models.ts:223`, `cropModels.ts:211`, `stumpModels.ts:291`

## Section D — Server tick

Tick period is 100 ms at `DEFAULT_TICK_HZ = 10`. Anything above that drops ticks
and stalls every connected client's `terrainDiff` delivery. Ranked by measured
stall.

### D1. A temple-placement press runs up to hundreds of full-budget A* searches synchronously
- **File:** `plugins/pilgrims/server/settling.ts:313` (`canDispatchSettler`), reached from the temple placement intent at `plugins/temples/server/index.ts:168` → `pilgrims-bridge.ts:114`
- **Mechanism:** `scanSettleSites` (`settling.ts:237-273`) sweeps `SETTLE_RING_SAMPLES(48) × SETTLE_DISTANCE_STEPS(16) = 768` anchors and calls `planRoute` → `findRoute` for every candidate passing `isBlockSettleable`, returning on the first success. `findRoute` returns null only after `expansions >= ROUTE_NODE_BUDGET` (65 536, `shared/src/pathing.ts:160-163,401`), and `ROUTE_SEARCH_MARGIN_CELLS = 128` makes the search box ~336² = 113 k cells — **larger than the budget**, so a walkable-but-disconnected candidate always exhausts it. `canFoundStructureAt` degrades to `true` when structures is absent (`structures-bridge.ts:16-17`), leaving walkability as the only filter.
- **Fix:** bound the *scan*, not just each search: (a) stop after the first N route attempts (a temple needing more than a handful is refused anyway); (b) reject candidates with a cheap connectivity test — a walkable-component labelling of the door's component, computed once per scan and reused for all 768. The press path must not run an unbounded search at all; answer it from the same cached labelling the epoch dispatch uses.
- **Skeptic's corrected cost:** measured (real `settling.ts` + `shared/src/pathing.ts`, synthetic 2048² world, no ports touched): temple at (1000,1000) with a 6-cell watercourse 10 cells east → `canDispatchSettler` **true in 4 582 ms** on a flat plateau and **656 ms** over rolling terrain; no barrier → 0.5 ms; island inside a moat → false in **132 ms** (cheap, because unwalkable goals early-out at `pathing.ts:373-374`). One full-budget failed `findRoute` = **27–33 ms**, not the claimed 49 — so `pathing.ts:154-156`'s own ~24 ms estimate is roughly accurate, not 2× optimistic. A succeeding 80-cell route is 0.3 ms. **One press blocks the event loop ~0.65 s on realistic terrain, up to ~4.6 s on open ground — 6 to 46 dropped ticks**, with every other player's intents queued behind it. "768 full-budget searches" is an upper bound.

### D2. A failed `findRoute` costs the full 65 536-expansion budget, and one settler scan triggers dozens
- **File:** `shared/src/pathing.ts:363` (`findRoute`; budget return :401, per-edge Map+heap work :437-441) → `plugins/pilgrims/server/settling.ts:237-273`
- **Mechanism:** same root as D1, at the tick-synchronous seams: `dispatch` (`settling.ts:567`, once per 25 s epoch but synchronous in one tick), `retryOrRetire` (:534), `emitFrom` (:633). `pathing.ts`'s own cost note reasons that routes are computed on goal-change events "at most a handful of times over one walker's whole lifetime" — that reasoning does not cover the settler scan, where every settleable-but-unreachable anchor before the first reachable one pays a whole search.
- **Fix:** two levels, both needed. (a) Contract: make the budget bound **work**, not expansions — add an elapsed-time budget derived from the tick period, and let callers hand in a *shared* budget so N searches in one turn cannot each spend a full one. (b) Caller: `scanSettleSites` must not use A* as a reachability filter — prefilter with a walkable-component id maintained incrementally off the terrain diff the world already produces, and run `findRoute` at most once per scan. Spreading replans across ticks (the mitigation `pathing.ts:158-160` names) does **not** help, because all the calls happen inside one `dispatch`.
- **Skeptic's corrected cost:** measured, direct import of `shared/src/pathing.ts`: one budget-exhausting `findRoute` = **26–46 ms, median ~29 ms**, at every settle-range goal distance (16/40/80 cells) on both 512² and 2048²; a succeeding route is 0.2 ms. Replaying the real 48×16 geometry for a temple 9 cells from a river on a large landmass: **32 failures / 934 ms at one bearing offset, 115 / 3 371 ms at another, 171 / 4 286 ms at the worst** — 0.9–4.3 s in ONE synchronous call, versus the 1.5 ms `settling.ts:114-116` claims. Two corrections: **"on an island" is NOT this bug** (a 30-cell island returns in <0.1 ms — the open set empties long before the budget; the real trigger is *big landmass, candidate across a river/cliff*), and **"~55 searches" understates it** — the bearing-outer/distance-inner ordering pushes the count into the hundreds (171 measured). **Overlap:** D1 and D2 are the same defect at two seams; fix them together.

### D3. Pilgrim dispatch re-runs a full-budget A* every tick for every settlement that cannot reach a settled monster
- **File:** `plugins/pilgrims/server/pilgrimage.ts:885` (`planRoute` inside the dispatch loop at :851-887)

### D10. Periodic snapshot blocks the tick loop and all outgoing sends

### D12. River network is fully retraced every 250 ms while any sim plugin sculpts
- **File:** `server/src/world/world.ts:1078` (`riverNetwork()`, :1078-1093; stale flag set on ANY non-empty diff at :1040-1050; `RIVER_RECOMPUTE_INTERVAL_MS = 250` at :120)
- **Mechanism:** `computeRiverNetworkFromSprings` is literally `springs.map(traceRiver)` (`shared/src/rivers.ts:874-881`) — nothing is reused across calls; 24 springs (`MAX_SPRINGS_PER_NETWORK`, :58) each traced against a `2 × worldSize = 4096`-cell budget. It is pulled **synchronously from inside the sculpt fan-out**: `sculpt-service.ts:71` → `host.ts:393-411` → `wildlife onTerrainChanged` → `reactToTerrain` → `despawnInvalidHabitat` → `isValidCellFor` → `sharedIsWalkableCell` → `world-api.ts:187 get freshwater` → `World.freshwaterMap()` → `riverNetwork()`. Issue #235 (`ce0cf89`) made spring **selection** incremental; the **trace** was left as a full recompute, so a 15-cell sculpt still re-traces every river.
- **Fix:** (1) retrace incrementally — keep per-river traced-cell sets and re-trace only rivers whose spring moved or whose course intersects the diff's neighbourhood (the `SpringIndex` already says which springs changed); (2) failing that, take it off the sculpt fan-out — mark stale in `applySculpt` and recompute at most **once per tick** from `PluginHost.tick` (`host.ts:296`) before plugins run. Do **not** raise `RIVER_RECOMPUTE_INTERVAL_MS`; that trades latency for the same total cost. The client already moved this identical computation off its critical thread (`client/src/render/water/riverNetworkWorker.ts:32-62`); the server runs it inline on its only thread.
- **Skeptic's corrected cost:** measured independently (2048² world, 400 unlocked chunks, 1 200 plugin-option sculpts → 745 candidates / 24 springs / 24 rivers / 28 547 traced points): **11.33 ms per recompute** (mean of 40); `springIndex.springs()` 0.080 ms, `freshwaterMap` rebuild +0.12 ms, one `applySculpt` 0.015 ms — so **>99 % is the trace, not spring selection**. At the 250 ms throttle: **~45 ms/s ≈ 4.5 % of the single server thread while sculpting**, plus an ~11 ms hitch inside a 100 ms tick. Two corrections: **"forever" is overstated** — sculpting plugins are event-driven, so this runs during bursts, not permanently; and on an unsculpted fresh 2048 genesis the same measurement is **0.001 ms with 0 springs** — cost scales with revealed-terrain jaggedness, saturating at 24 springs. The cited `.gpu-perf` line (`1934.7 ms get freshwater / 100.1 s`) is a **pre-`ce0cf89`** profile dominated by `selectSprings` (2 562.2 ms self) and corroborates the call chain only, not this cost. Severity **medium-high**, not high — an overrun only at a raised `TICK_HZ`.

### D13. Every plugin sculpt copies the whole heightmap, once any column in the world has been carved
- **File:** `shared/src/heightmap.ts:1937` (`buildLayerView`: `map.cells.slice()` + `new Uint8Array(map.cells.length)`, brush-radius-independent), gated at `:2052` on `spanBand === null && map.columnSpans.size === 0`

Per-tick callers: `plugins/volcanoes/server/vents.ts:416-421` and `:600-601` (`meltCell` in the front-advance loop), `plugins/mudslides/server/terrain.ts:172`, `plugins/storms/server/surge.ts:148`. Carve is a player-facing tool, so `columnSpans.size > 0` is the normal state of a played world.
- **Fix:** size the layer view to the **pass box**, not the world. `smooth` already computes the seed bounding box and grows it one ring per pass, capped by `SMOOTH_PASS_LIMIT`, so the maximum extent is known before the copy — allocate `heights`/`excluded` for that window and index through its origin, or drop the dense copy for a lazily-seeded `Map<index,height>`. Either turns O(world) into O(edit). Do **NOT** narrow the gate to `spanBand !== null`; that would silently change layered-world relax behaviour. The copy is the defect, not the condition.
- **Skeptic's corrected cost:** reproduced independently (identical cloned start states differing only by one carved column, radius-4 plugin-option stroke changing 25 cells, median of 41): **512² +0.33 ms, 1024² +0.40 ms, 2048² +2.03 ms median / 8.94 ms max** — lower than the claimed 4.38 ms, same O(world-area) defect. ~12.6 MB allocated+copied per sculpt at 2048² regardless of brush radius. Frequency corrected: `drainPendingConeSculpts` does **not** pay this every tick (it returns immediately on an empty queue, `vents.ts:417-419`); the strongest multiplier is mudslides' `MAX_STEPS_PER_TICK = 8` (`slides.ts:278`) → **up to ~16 ms of a 100 ms tick**; the common 1–2 sculpts/tick case is ~2–4 ms/tick. Residual not rulable read-only: whether all three plugins are enabled by default (changes how often, not whether).

### D14. Boats rescan a 748-cell coastal disc for every under-strength village every tick, forever for inland ones
- **File:** `plugins/boats/server/fleet.ts:408` (`advanceShipyards`; `boats.filter(...)` allocation at :410, `launchCell` at :415, disc walk at :263-278)
- **Mechanism:** runs every tick from `advanceFleet` (:627 ← `index.ts:91`), ahead of the broadcast interval gate. `launchCell` early-returns only once `COASTAL_MIN_WATER_CELLS = 32` sailable cells are found, so an **inland** village walks all 748 offsets every tick for the life of the world and produces nothing. The roster has no coastal filter — `events.ts:94` gates on tier only.
- **Fix:** cache coastality per village (compute `launchCell` once when the village is remembered, invalidate on a sculpt near it — boats has no `onTerrainChanged` today; adding one is the seam). Store the afloat count on the village record instead of re-filtering the fleet array each tick.

The submitted 4.1 ms/tick figure requires **512 simultaneous tier-1 inland villages**, which `STRUCTURES_CAP` bounds but does not evidence — that cap covers all live structure cells, and villages are the strict tier≥1 subset. At the only village count with observational support (seven tier-1 settlements, `boats/protocol.ts:230-240`) this is **43 ms per 100 s**, comparable to weather's 20 ms/100 s on a server measured 10 % busy. Real unbounded-work path, correct fix, **impact low, not medium.**

### D15. World-invariant scalars are exposed only as revocable getters, so hot plugin loops pay a call + null check per read
- **File:** `server/src/plugins/world-api.ts:146` (`get worldSize() { return bound('worldSize').world.size; }`; `bound()` null-test at :130-143)
- **Mechanism:** `worldSize`, `chunksPerEdge` and `difficulty` are constant for the life of a session but dispatch through that closure on every read. The per-tick chain has no adapter: `plugins/structures/server/index.ts:822` `onTick(world: WorldApi)` → `simulate` → `advanceLife` → `life.ts:854` → `:890 scanChunk`; `StructuresWorld` is a structural slice of `WorldApi`, so the object in the per-cell loop **is** the revocable api.

Note this does weaken the deliberate revocation contract documented at `:126-137` (owner decision 2026-08-25, throws rather than no-ops) — an owner call, not a cost objection; a stale integer world size is harmless where a stale `heightAt`/`sculpt` would not be.
- **Skeptic's corrected cost:** V8 self-time trace (`.gpu-perf/results/2026-08-28-server-fresh2048.txt`, 100.1 s sample, 10.20 s busy): **417.7 ms SELF in `get worldSize` — 4.1 % of server busy time, 0.42 % of wall, 7th in the self table, above `relaxPair` (320.2 ms) and `smooth` (304.1 ms)**. Server-tick only; zero client-frame effect. Read traffic is **understated** by the finding, not overstated: `scanChunk` reads `world.worldSize` once per scanned cell at `life.ts:731` *before* any early-out, plus `isBuildableCell` at `suitability.ts:216` (×2), `:67` (×2 per orthogonal neighbour) and `:181` (×2 per footprint neighbour) — **tens of dispatches per buildable cell**, not "twice per call". **The `surveyLairs` attribution is FALSE and must be struck**: `habitat.ts:837` hoists `const size = world.worldSize` once per survey; the monsters-side getter caller is `isLairCell` (`habitat.ts:314`). ## Cross-cutting observations

1. **`addUpdateRange` is the single most repeated omission.** The repo already
   uses it correctly in exactly two places — `client/src/render/terrainMeshes.ts:947`
   and `plugins/volcanoes/client/lavaFlow.ts:558-562` — and every other
   instanced/attribute renderer flags `needsUpdate` bare: flora (grass, fringe,
   trees, crops, stumps), structures (buildings, skiffs), storms (spiral, funnel),
   volcanoes (plume). That is C1, C2, A4, A7 and half of B4. It is a **contract
   defect, not five callsite bugs**: three's `updateRanges.length === 0` branch
   uploading the whole capacity array is a footgun that every renderer author
   here has stepped on. The durable fix is a shared helper (`uploadPrefix(attr, count)`)
   used by every rig, not five independent patches.

2. **"Rebuild the world for a local change" is the second pattern.** B1, B3, B5,
   B6, C2, D4, D5, D6, D12 and D13 are all the same shape: a cell-exact diff
   arrives, and the consumer discards its entire derived state and rebuilds it.
   In every case the incremental information is *already available* at the seam
   (`onTerrainChanged`, the diff cell list, the chunk index, `SpringIndex`).

3. **A* budget exhaustion is a load-bearing server hazard.** D1, D2 and D3 are
   one root cause: `findRoute` bounds *expansions*, not *work*, and callers use a
   full A* as a reachability predicate. A walkable-component labelling maintained
   off the terrain diff would collapse all three at once, and is the single
   highest-value server change in this report.

4. **Comments in this codebase are not evidence.** Measurements contradicted the
   in-file cost claim at `habitat.ts:686-690`, `life.ts:972-974`, `census.ts:91-95`,
   `site.ts:68`, `spiral.ts:9-11`, `fringeModels.ts:31`, `sky.ts:156-158`,
   `host.ts:375` and `fire/client/index.ts:467`. Several are stale by a
   world-resample; several were never true. Worth a sweep of its own.
