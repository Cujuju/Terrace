# Arena review (1016223 + 64ce9cf), 2026-08-29 — 15 held, 0 refuted (3 Opus lenses, 1 Opus skeptic per finding)

## 1. [high/correctness] Compaction's cost estimate omits the hole, so a budgeted frame can upload 14× its budget
`client/src/render/terrainMeshes.ts:996`

**Claim:** `compactSuperMesh` charges a move `run.count * ARENA_TRANSFER_MS_PER_VERTEX`, but `moveRunDown` declares `addRange(sm, to, runEnd - to)` — `run.count + hole.length` vertices, because the vacated tail is zeroed and must be uploaded too. The estimate is short by exactly the hole's length, and since a move preserves the hole's length, every subsequent move in the same sweep is short by the same amount. The budget therefore does not bound the transfer it was written to bound.

**Scenario:** Traced and then measured on a fixture of 16 chunks in one super-mesh: chunk 0 at 141,996 vertices (a developed chunk), the other 15 at 5,388 (the owner's world median). Chunk 0 is levelled to 3 vertices, opening a ~142k hole with small runs above it. On the next frame — one that spliced, so `ARENA_COMPACT_STROKE_BUDGET_MS` = 1.0 ms applies, i.e. 52,631 vertices at ARENA_TRANSFER_MS_PER_VERTEX — compaction made 5 moves, charging 5 × 5,388 × 19e-6 = 0.51 ms, while the four attributes' updateRanges came to 747,696 vertices: 5 × (141,996 + 5,388). At 19 B/vertex that is 14.2 MB and ≈14.2 ms of transfer declared on one frame against a 1.0 ms budget, the same order as the 19–21 MB/step regression commit 64ce9cf exists to remove. The larger the freed chunk, the worse the ratio, and the shrink of a big chunk is exactly what opens a big hole.

**Skeptic:** The code confirms the gap: `compactSuperMesh` charges only `run.count * ARENA_TRANSFER_MS_PER_VERTEX` (terrainMeshes.ts:996) while `moveRunDown` ends with `addRange(sm, to, runEnd - to)` (terrainMeshes.ts:974), i.e. run.count + hole.length vertices, since the vacated tail is zeroed (`zeroVertices`, :970) and must be re-uploaded. Nothing downstream shrinks that: `addRange` only clamps to `[0, liveEnd)` (:837-848) and `addVertexRange` forwards each range to three unmerged, and the vacated hole re-inserted at :972 has exactly the original hole's length, so every further move in the same sweep repeats the same undercharge. The estimate therefore does not bound the declared transfer, and a large freed chunk (big hole, small runs above it) makes the ratio arbitrarily bad exactly as described.

## 2. [medium/correctness] The shared compaction budget is spent in map order, so a fragmented early super-mesh starves the rest
`client/src/render/terrainMeshes.ts:1014`

**Claim:** `compact` walks `superMeshes.values()` from the beginning every frame and returns as soon as `spentMs >= budgetMs`. Iteration order is the map's insertion order and is never rotated, so a super-mesh that keeps generating holes consumes the whole frame budget and the super-meshes after it are never reached — their dead space is never reclaimed while the stroke continues.

**Scenario:** A radius-4 brush straddles a super-mesh boundary (SUPER_MESH_SPAN_CHUNKS = 8, so the boundary falls every 32 world units and a held stroke crosses one routinely). Super-mesh A was created first, so it is first in the map. Each stroke step dirties a chunk in A and one in B; A's splice opens a hole, and compaction spends the frame's 1.0 ms closing A's holes and returns before touching B. B accumulates one dead run per stroke step for the whole stroke, growing its liveEnd — and therefore its draw range and vertex-shader cost — with dead vertices, and pushing it toward the one upload the arena does not bound, a capacity doubling (plan §5). Only a frame on which A happens to have no affordable move lets B compact at all.

**Skeptic:** `compact` (client/src/render/terrainMeshes.ts:1014-1021) iterates `superMeshes.values()` in fixed insertion order with `if (spentMs >= budgetMs) return;` and no rotating cursor anywhere (grep shows no cursor/rotation state), so a first-in-map super-mesh with affordable moves each frame does consume the shared 1.0 ms and later super-meshes are never reached — the mechanism is exactly as claimed. The only mitigation I found is the unbudgeted pre-doubling sweep at line 1147-1151, which blunts the "unbounded doubling upload" half of the scenario for the starved mesh but not the dead space inflating its `liveEnd` and draw range for the length of the stroke. Whether A actually sustains ≥1.0 ms of affordable moves every frame is workload-dependent (one hole per step often runs A dry), so severity may be lower than stated, but the scenario is not structurally impossible.

## 3. [low/correctness] A super-mesh created mid-pass does not set reallocatedThisPass, so its first splices' ranges are uploaded twice
`client/src/render/terrainMeshes.ts:1042`

**Claim:** `reallocatedThisPass` exists because three's create path (`WebGLAttributes.update` with no cached buffer) does a full `bufferData` WITHOUT clearing `updateRanges` — only `updateBuffer` clears them (verified in node_modules/three/src/renderers/webgl/WebGLAttributes.js:36-78 and :147). `ensureSuperCapacity` sets the flag before `bindGeometry`, but `createSuperMesh` installs equally brand-new, never-uploaded attributes with the flag hard-coded `false`, so the same double-upload it guards against is left open on the creation path.

**Scenario:** A pass in which two chunks of a not-yet-existing super-mesh are spliced: the first `spliceAnswer` calls `createSuperMesh` (flag false) and `addRange` records the run; the second splice records its own ranges. At render, `createBuffer` uploads the whole array and leaves both ranges on the attribute. The next frame's first splice bumps `version`, and `updateBuffer` then re-uploads those stale ranges alongside the new one — two extra chunk runs × 4 attributes of `bufferSubData` for data the GPU already has. Bounded by a chunk rather than by the arena, so it is far smaller than the two findings above, but it is the exact failure the field was added to prevent and the one place it is not applied.

**Skeptic:** Verified end-to-end: three's create path (node_modules/.pnpm/three@0.185.1/.../WebGLAttributes.js:204 → createBuffer :5-77) does a full bufferData and never clears updateRanges, while only updateBuffer clears them (:147). createSuperMesh (client/src/render/terrainMeshes.ts:1030-1049) binds brand-new, never-uploaded attributes with reallocatedThisPass hard-coded false (:1042), and spliceAnswer splices into it immediately (:1306-1307), so addRange (:838, which short-circuits only on that flag) records ranges that survive the first render's bufferData and get replayed by the next updateBuffer. The scenario stands, though it is perf-only and bounded by that pass's chunk runs, not a visual/correctness defect.

## 4. [high/perf-contract] Case-4 splice re-uploads the whole hole surplus, which is bounded by the arena and not by the chunk
`client/src/render/terrainMeshes.ts:1143`

**Claim:** When a grown run is placed by first-fit (`takeHole`), `spliceChunk` adds a dirty range covering the entire surplus of the split hole: `if (reused.surplus > 0) dirtied.push([reused.offset + count, reused.surplus])`. That surplus region is untouched by this splice — every hole on the free list was already zeroed by `zeroVertices` AND already uploaded when it was created (case 2's `[slot.offset, old]` range, case 4/5's `[freedOffset, old]` range, or `moveRunDown`'s `addRange(to, runEnd - to)`), so the GPU copy is already zeros there. Splitting a hole changes only the free-list bookkeeping, never a byte of the buffer. The range is therefore pure redundant transfer, and its size is the size of the largest hole the first-fit scan lands on — unbounded by the spliced chunk. The plan's stated bound is `(count + old) x 19 B per touched chunk + one move`; this range is outside it, and the commit's own upload-bound test only exercises case 5 (append, no hole fits), so nothing pins case 4.

**Scenario:** On the owner's world, a p99 chunk of ~142 k vertices is flattened and re-splices at ~5 k, leaving a ~137 k-vertex hole low in the arena. The player then sculpts a neighbouring chunk in the same super-mesh that grows 6 k -> 7 k and does not end at `liveEnd`, so it takes case 4. `takeHole` returns the lowest hole that fits — the 137 k one — with `surplus = 130 k`. The splice's ranges are 7 k (new run) + 130 k (surplus, already zeros on the GPU) + 6 k (old run) = ~143 k vertices x 19 B = 2.7 MB of `bufferSubData` on a stroke frame, against a claimed bound of (7 k + 6 k) x 19 B = 0.25 MB and the 1.8 MB slow-frame target. At the measured ~1 ms/MB that is ~2.7 ms on the splice frame plus roughly as much again in GPU-process backpressure on the next — the exact spike shape the arena was built to remove.

**Skeptic:** Every hole on the free list is zeroed and uploaded at the moment it is created — terrainMeshes.ts:1123-1124 (case 1/2), :1168-1169 (case 4/5), :970-973 (moveRunDown's zeroVertices + addRange(to, runEnd-to)) — and the one path that skips addRange (reallocatedThisPass, :838) is precisely the path where three re-uploads the whole buffer, so a split hole's surplus is already zeros in the GPU copy and `dirtied.push([reused.offset + count, reused.surplus])` at :1143 transfers nothing new. Its size is the size of whichever hole first-fit lands on (takeHole scans lowest-first, :914-931) and is therefore unbounded by the spliced chunk, so a large hole left by a flattened p99 chunk plus a neighbouring case-4 grow reproduces the scenario as described. Nothing pins it: the upload-bound test (terrainMeshes.test.ts:971-1022) asserts ranges only for the case-5 append, while the first-fit test (:1098-1129) asserts layout and liveEnd, never updateRanges.

## 5. [high/perf-contract] Case-5 splice runs an unbudgeted full compaction sweep, so a splice can move every run and upload the whole arena
`client/src/render/terrainMeshes.ts:1151`

**Claim:** `spliceChunk`'s append path calls `compactSuperMesh(sm, Infinity)` when the append would exceed capacity and any hole exists — the one place a sweep runs with no budget, on a stroke frame, inside the frame hook. A full sweep is up to one `moveRunDown` per run (63 runs on a full super-mesh), and every `moveRunDown` does a `copyWithin` of the run in all four attributes plus `markDirty` + `addRange` over `[hole.offset, oldRunEnd)`. The sum of those ranges is the whole live arena, so this single splice's upload is the super-mesh — precisely the 19-21 MB failure the commit says it removed, just moved from the packed tail move to the compactor. It also does not necessarily avoid the growth it is trying to avoid: if `liveCount + count` still exceeds capacity after the sweep, `ensureSuperCapacity` doubles anyway and the frame pays a full-arena `copyWithin` sweep AND a full `bufferData`. The scan itself is quadratic too: the inner loop `break`s and restarts at hole 0 after every move, and each hole costs an O(64) `runStartingAt`, so a 64-move sweep is ~64 x 65 x 64 ≈ 266 k slot comparisons.

**Scenario:** A super-mesh at capacity holding 64 runs and a scattered free list (the steady state after a long stroke over a developed area — the commit's own history test produces exactly this shape). The next stroke step grows one chunk; the run is not at `liveEnd`, no single hole fits, and `sm.liveEnd + count > capacityVertices(sm)`. The frame hook, already having spent CHUNK_SPLICE_FRAME_BUDGET_MS, then compacts to exhaustion: ~1.25 M vertices copied on the CPU and ~24 MB of `addUpdateRange` handed to three, ignoring both ARENA_COMPACT_STROKE_BUDGET_MS (1.0) and ARENA_COMPACT_IDLE_BUDGET_MS (3.0). That is a >20 ms frame, and the whole point of `compactSuperMesh` taking a `budgetMs` is bypassed at the one callsite that runs mid-stroke.

**Skeptic:** The code matches the claim: terrainMeshes.ts:1149-1151 calls `compactSuperMesh(sm, Infinity)` in case 5 whenever `sm.liveEnd + count > capacityVertices(sm) && sm.holes.length > 0`, and `spliceChunk` runs inside `drain(CHUNK_SPLICE_FRAME_BUDGET_MS)` in the frame hook (line 1449), so ARENA_COMPACT_STROKE_BUDGET_MS/IDLE budgets are genuinely bypassed there; the loop at 987-1005 does one `moveRunDown` per iteration, each with a four-attribute `copyWithin` plus `addRange(sm, to, runEnd - to)` (955-1008), so a full sweep's ranges can sum to the live arena, and the O(64) `runStartingAt` per hole with a `break`-and-restart makes the scan quadratic. The comment at 1146-1150 acknowledges this is deliberate ("the one place a sweep runs without a budget"), and `ensureSuperCapacity` (730) can still double afterwards, so the claim's second point holds too — the finding is a design tradeoff the author chose, not a misreading, and the scenario is reachable as described.

## 6. [medium/perf-contract] compact() rescans every super-mesh and every hole each frame even when no move is affordable, making zero progress
`client/src/render/terrainMeshes.ts:1014`

**Claim:** `compact` is called unconditionally from the frame hook and iterates every super-mesh with `holes.length > 0`; it only returns early on `spentMs >= budgetMs`, which never happens if nothing was moved. Inside, `compactSuperMesh` walks the free list and calls `runStartingAt` — an O(SUPER_MESH_SPAN_CHUNKS^2) linear scan of the slots map — for EVERY hole before checking whether the run above it fits the budget (`const run = runStartingAt(...)` precedes `if (spentMs + costMs > budgetMs) continue`). When no run is affordable, the whole scan is repeated every frame forever with no state change and no progress. The commit's own doc names this state as a residual ("a chunk at the CHUNK_TRIANGLE_BUDGET ceiling ... would not fit even here and is the named residual"), but it treats the residual as only a stalled hole, not as a recurring per-frame walk.

**Scenario:** A revealed 512-world-unit map is 256 super-meshes. Several hold holes whose run above exceeds ARENA_COMPACT_IDLE_BUDGET_MS (3.0 ms = ~157 k vertices, reachable well under the 393 k CHUNK_TRIANGLE_BUDGET ceiling). Every idle frame thereafter runs `compact(3.0)`, which for each such super-mesh does `holes.length` x 64 slot comparisons and moves nothing — a fixed, permanent per-frame CPU tax on a 7.1 ms budget for work that is known in advance to be unaffordable. Cheap fix: order the budget check before `runStartingAt`, and skip a super-mesh whose cheapest candidate was already rejected at this budget.

**Skeptic:** The mechanism is exactly as described in the current file: the frame hook calls `compact(...)` unconditionally (terrainMeshes.ts:1450), `compact` skips only super-meshes with zero holes and returns early only on `spentMs >= budgetMs` (1014-1021), and `compactSuperMesh` calls `runStartingAt` — a linear scan of the ≤64-entry slots map (936-941) — for every hole before the budget test `if (spentMs + costMs > budgetMs) continue` (992-997), so a stalled super-mesh is re-swept every frame with no progress. That stalled state is reachable: the code's own comment at 219-224 concedes a run up to CHUNK_TRIANGLE_BUDGET's 393 k vertices (~7.5 ms) exceeds the 3.0 ms idle budget. I would only downgrade the severity — the wasted work is bounded and allocation-free (≤ ~65 holes × 64 comparisons per stalled super-mesh), not that the scenario is impossible.

## 13. [medium/tests] 'leaves no hole behind once flush has built everything' passes with a budgeted compaction

**Claim:** The test's premise is that `flush()` ends with `compact(Infinity)` — "build everything now" also means "and leave no holes". Its fixture's runs are 300–1500 vertices, i.e. ~0.006–0.03 ms of estimated transfer against ARENA_COMPACT_IDLE_BUDGET_MS = 3.0, so a budgeted sweep finishes too. **Scenario:** `flush`'s compaction acquires a budget (or the budget is applied to the no-scheduler path by an accident of refactoring).
